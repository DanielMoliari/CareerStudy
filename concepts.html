01. Event Loop

Como JavaScript faz uma so thread parecer concorrente — call stack, microtask queue e macrotask queue dancando juntos.

P1
call stack microtasks (Promise.then) macrotasks (setTimeout, IO) em execucao
passo 0 / 8
Click proximo passo. Vamos rodar este codigo: console.log(1); setTimeout(()=>log(4),0); Promise.resolve().then(()=>log(3)); console.log(2)

O event loop e um loop infinito que so faz uma coisa: se a stack ta vazia, pega proximo task. A pegadinha esta na ordem das filas. Toda vez que a stack esvazia, ele drena 100% da microtask queue antes de tocar em qualquer macrotask. Por isso Promise.then sempre roda antes de setTimeout(..., 0) mesmo que voce agende o timeout primeiro. Em Node tem fases extras (timers, pending, poll, check, close), mas a regra de microtasks-primeiro vale igual.

02. CAP Theorem

Em uma particao de rede, voce escolhe consistencia OU disponibilidade. Nao tem como ter as duas — e ninguem desliga a particao.

P1
Click numa das opcoes acima pra ver quais bancos de dados ficam em cada lado do triangulo.

Brewer disse: dado um network partition (computadores nao conseguem falar), voce so pode escolher 2 de 3. Como P (tolerancia a particao) nao e opcional em sistema distribuido (rede sempre falha), a escolha real e entre C ou A. PostgreSQL com sync replicas escolhe C (recusa write se replica caiu). Cassandra escolhe A (aceita write em qualquer no, reconcilia depois). DynamoDB e tunable — voce decide por request. PACELC estende o teorema: mesmo sem particao, else tradeoff entre Latency e Consistency.

03. MVCC (Postgres)

Como dois clientes leem e escrevem a mesma tabela ao mesmo tempo sem travar nada — cada transacao ve um snapshot.

P1
No MVCC, cada UPDATE cria uma nova versao da linha (v2). Quem comecou antes continua vendo a versao antiga (v1) ate dar COMMIT. Sem locks pra leitura.

MVCC = Multi-Version Concurrency Control. Em vez de bloquear leitores enquanto alguem escreve, o Postgres mantem multiplas versoes da mesma linha. Cada tupla tem xmin (transacao que criou) e xmax (transacao que deletou). Cada transacao recebe um snapshot no BEGIN e so enxerga versoes commitadas antes desse snapshot. Resultado: readers nao bloqueiam writers, writers nao bloqueiam readers. O custo e o lixo (tuplas mortas) que o VACUUM precisa limpar — se nao roda, a tabela incha (table bloat).

04. B-tree vs LSM-tree

Duas filosofias opostas pra indexar dados em disco — uma otimiza leitura, outra otimiza escrita.

P1
Regra de bolso: read-heavy + dados que mudam em lugares aleatorios → B-tree. Write-heavy + time-series ou logs → LSM. Bancos modernos misturam (ex: Postgres ja tem extensoes columnar).

B-tree e in-place: cada UPDATE reescreve a pagina onde a chave mora. Bom pra leitura (3-4 IOs ate o leaf), ruim quando ha muitos writes random — page splits ficam caros. LSM nunca escreve in-place: tudo vai pra um memtable em RAM e, quando enche, flusha pra um SSTable imutavel. Isso da escritas sequenciais (turbinadas). O preco e ler de varios SSTables de uma vez, e o background compaction que merge esses arquivos gera write amplification (o mesmo dado e reescrito muitas vezes). Bloom filters ajudam a pular SSTables sem a chave.

05. TLS Handshake

A dancinha entre cliente e servidor pra concordar numa chave secreta sem ninguem no meio descobrir.

P1
Click numa das mensagens acima pra ver o que ela carrega.

O TLS handshake resolve dois problemas: autenticar que voce realmente esta falando com o servidor (via certificado assinado por CA confiavel) e derivar uma chave simetrica compartilhada sem expor segredo. Em TLS 1.3 isso virou 1-RTT: ja na primeira ida o cliente manda um KeyShare ECDHE, e o servidor responde com o seu, e ambos derivam a mesma chave sem nunca transmiti-la. PFS (Perfect Forward Secrecy) garante que mesmo se a chave privada do servidor vazar amanha, sessoes antigas continuam ilegiveis — porque cada handshake usa keypair efemero.

06. HTTP/1.1 vs HTTP/2 vs HTTP/3

A evolucao do head-of-line blocking — a saga de fazer o request HTTP nao parar quando um pacote se perde.

P2
HTTP/1.1

Texto plano. 1 request por conexao TCP em ordem. Pipelining quase ninguem usa por bug. Browser abre ate 6 conexoes paralelas pra mesmo host.

HTTP/2

Binario. Multiplexa varios streams numa so TCP. HPACK comprime headers. Mas como TCP entrega em ordem, 1 pacote perdido para todos os streams (TCP HOL).

HTTP/3

Roda em QUIC (sobre UDP). Streams realmente independentes. TLS embutido no transporte. 0-RTT em retomadas. Connection migration: troca de wifi sem derrubar.

Cada versao tenta matar o head-of-line blocking. HTTP/1.1 trava no nivel da aplicacao (1 request por vez). HTTP/2 multiplexa, mas como tudo passa por 1 socket TCP, perda de pacote trava todo mundo no kernel — TCP entrega bytes em ordem. HTTP/3 mudou pra UDP e implementa controle de fluxo em user space, fazendo cada stream realmente independente. Bonus do QUIC: connection ID independe de IP — voce migra de wifi pra 4G sem dropar a conexao.

07. RAG Pipeline

Como dar memoria pro LLM sem retreinar — busca semantica + prompt augmentation.

P1
1
Query

Pergunta do usuario chega em texto natural. Pode ser reescrita (HyDE, query expansion) antes de seguir.

2
Embed

Modelo de embedding (text-embedding-3, e5, bge) transforma texto em vetor de 768/1536/3072 dims. Mesmo modelo usado offline pra indexar precisa ser usado online pra buscar.

3
Vector DB — kNN

Busca top-K vetores mais proximos por cosine/dot. ANN (HNSW, IVF, ScaNN) trocando recall por latencia. Pinecone, pgvector, Qdrant, Weaviate, Chroma sao as opcoes comuns.

4
Rerank

Cross-encoder (BGE reranker, Cohere rerank) reordena os candidatos com modelo mais caro mas mais preciso. K=50 → top 5. Faz diferenca real em qualidade.

5
Augment

Monta prompt: system + contexto recuperado + pergunta. Cuidado com ordem (LLMs ignoram meio do prompt — lost in the middle) e com tokens (caro).

6
LLM

Geracao final com citation. Considere streaming, fallback se nada relevante (sem alucinar), e logging pra avaliacao com ragas/llm-as-judge.

RAG (Retrieval-Augmented Generation) e o jeito padrao de injetar conhecimento privado num LLM sem fine-tuning. Voce indexa documentos uma vez (embeddings em vector DB), e em cada query: recupera os trechos mais parecidos, aumenta o prompt com eles, manda pro modelo. As pegadinhas reais: chunking (muito grande perde precisao, muito pequeno perde contexto), recall ruim (use rerank!), lost in the middle (LLM ignora meio do contexto), e avaliacao (groundedness, answer relevance, context precision).

08. Circuit Breaker

Pare de mandar request pra um servico que ja sabemos que ta caido — falha rapido, deixa ele se recuperar.

P1
estado: CLOSED · falhas: 0/3
Use os botoes pra simular: 3 falhas seguidas abrem o circuit. Depois do timeout vai pra HALF-OPEN. Um request OK la fecha de volta.

Circuit breaker (Hystrix, resilience4j, Polly) evita o cenario classico de cascading failure: servico downstream caiu, cada request seu trava 30s no timeout, sua thread pool esgota, voce tambem cai. A maquina de 3 estados — CLOSED → OPEN → HALF-OPEN → CLOSED — desacopla o caller do callee. Combinado com bulkheads (pools separados), timeout agressivo e fallback sensato, te da resiliencia. Em microservicos modernos, isso geralmente vive no service mesh (Istio, Linkerd) ou em libs cliente.

09. Consistent Hashing

Adicionar/remover servidor sem reorganizar 100% das chaves — o truque por tras de Cassandra, DynamoDB e CDNs.

P2
nos: 3 · chaves: 5
Comece com 3 nos. Adiciona um quarto e ve quantas chaves precisaram ser realocadas — so a fatia entre o no anterior e o novo.

Hash modular ingenuo (node = hash(k) % N) e um pesadelo: muda N de 4 pra 5 e quase 100% das chaves trocam de no. Consistent hashing mapeia tanto nos quanto chaves no mesmo anel circular (geralmente 0 a 2^32). Cada chave vai pro proximo no no sentido horario. Adicionar um no roubando uma fatia do ring afeta apenas 1/N das chaves. Pra evitar hot spots usa-se virtual nodes — cada servidor fisico tem 100-200 pontos no ring, distribuindo a carga melhor. Cassandra, DynamoDB, Riak, Memcached client (Ketama), CDNs internas — tudo isso usa.

OSI tem 7 camadas no modelo teorico. TCP/IP real agrupa em 4 (Link, Internet, Transport, Application). A regra mental: cada camada de baixo encapsula a de cima — HTTP virou bytes, bytes viraram TCP segments, segments viraram IP packets, packets viraram Ethernet frames. Quando entrevistador pede pra voce "tracear a request", voce passeia camada por camada — DNS resolve, TCP handshake, TLS handshake, HTTP request, app responde. Saber em qual camada cada problema acontece (timeout = L4, certificado errado = L6, 500 = L7) e o que diferencia debugging amador de profissional.

11. CQRS + Event Sourcing

Separa command (escrita) de query (leitura), e em vez de salvar estado, salva os eventos que levaram a ele.

P1
Event Sourcing = source of truth e o log de eventos (nao o estado). CQRS = comandos vao num modelo, queries em outro. Frequentemente usados juntos, mas sao independentes.

CQRS (Command Query Responsibility Segregation) separa o lado de escrita do lado de leitura. Voce pode usar Postgres pra command, Elasticsearch + Redis pra query, atualizando via eventos. Vantagens: scaling independente, queries denormalizadas turbinadas, modelos otimizados pra cada uso. Event Sourcing vai mais fundo: em vez de gravar o estado atual, voce grava cada evento que mudou o estado (UserCreated, EmailChanged). O estado vira uma funcao de replay sobre o log. Beneficio brutal: auditoria total, time travel, novos read models historicos. Custo: complexidade real, eventually consistent, snapshot pra performance, schema evolution dos eventos e dor.

12. JWT — JSON Web Token

Three dots, three pieces — header, payload, signature. Stateless auth no formato canonico.

P2
HEADER
{
  "alg": "HS256",
  "typ": "JWT"
}
PAYLOAD (claims)
{
  "sub": "1234567890",     // subject (user id)
  "name": "Daniel",
  "iat": 1716239022,       // issued at
  "exp": 1716242622,       // expiration (epoch)
  "iss": "https://auth.x", // issuer
  "aud": "api.x"           // audience
}
SIGNATURE
HMACSHA256(
  base64UrlEncode(header) + "." +
  base64UrlEncode(payload),
  SECRET_KEY
)
Atencao: payload e so base64 — nao e criptografado. Quem tiver o token le tudo. Se precisa esconder dado, use JWE (encrypted) ou nao bote no JWT.

JWT e stateless: o servidor nao guarda sessao, todo estado vai dentro do token assinado. Cliente manda Authorization: Bearer eyJhbGc..., server valida assinatura com a chave (HMAC simetrica ou RSA/EC asimetrica). Vantagem: escala lindo. Desvantagens reais que cobram em entrevista: nao da pra revogar facil (e por isso voce usa expiracao curta + refresh token), algoritmo "none" e CVE classico (sempre valide alg explicitamente), confusao HS vs RS (atacante envia token assinado com a public key como se fosse HMAC), e payload visivel — qualquer um faz atob(token.split(".")[1]) e ve seus claims.
